[GitHub repo](https://github.com/proteus-ui/proteus)

Proteus is a small React library built around one stubborn idea: **components do the work, themes do the look.** Core gives you markup, accessibility, and state. Color, type, and radius live in a stylesheet. Nothing in core invents styles at runtime — no CSS-in-JS, no theme provider, no style registry.

If you already write CSS or Tailwind, you can keep doing that. Proteus just gives you stable hooks to hang those styles on.

## The three packages

Think of it as a contract in the middle, with behavior on one side and paint on the other.

## How styling actually works

Three things make up the public styling API. Rename any of them and you break every theme and every consumer.

**Slots.** Parts of a component have names such as `root`, `icon`, and `title`. You pass a `classNames` map; the string can be a Tailwind utility list, a CSS module hash, or a class you wrote in a plain `.css` file. Proteus never looks inside that string.

With Tailwind, put utilities on the slot and drive states from the same `data-*` attributes the component already emits:

```tsx
<Button
  intent="danger"
  icon={<Trash />}
  classNames={{
    root: "rounded-full px-6 shadow-sm data-[disabled]:opacity-40",
    icon: "text-amber-500",
  }}
>
  Delete
</Button>
```

With CSS Modules, keep the class local and still hang it on the slot:

```css
/* SaveButton.module.css */
.root {
  border-radius: 999px;
  letter-spacing: 0.04em;
}
.icon {
  color: #f59e0b;
}
```

```tsx
import styles from "./SaveButton.module.css";

<Button classNames={{ root: styles.root, icon: styles.icon }}>Save</Button>;
```

Plain CSS follows the same idea: write `.my-cta { … }` and pass `classNames={{ root: "my-cta" }}`.

**`data-*` attributes.** State lives on the DOM. Disabled is `data-disabled`. A danger button is `data-intent="danger"`. An open dialog is `data-state="open"`. You write selectors against those the same way you would against `:hover`. In Tailwind that looks like `data-[state=open]:…`; in a stylesheet it looks like `.pr-dialog[data-state="open"]`.

**Tokens.** CSS variables are named for meaning, not for a swatch: `--pr-color-action-primary` and `--pr-color-text`, never `--pr-pink-500`. Dark mode or a rebrand is a new set of values for the same names.

Core’s own CSS is boring on purpose: a `pr-` prefix, one class, no nesting, no `!important`. The theme paints. Your class wins over ours.

## Why bother, if MUI already exists

We are not the library everyone already has in `package.json`. We do not ship a date picker, a data grid, or a component for every tag in the HTML spec. That is intentional.

Where Proteus is the better fit:

**You keep your styling stack.** Most popular libraries marry you to one engine — Emotion, styled-components, their own `sx` prop, or a Tailwind-only kit. Proteus does not. The same `Button` works in a Tailwind app, a CSS Modules app, and a plain-CSS app. We want you to keep writing styles the way the rest of the repo already does.

**Appearance is a file, not a runtime.** There is no theme provider, no style injection on the server, and no `useServerInsertedHTML`. You import CSS. Next App Router does not have to treat the design system as a special client island. That is a technical win even when the catalog is still small.

**The contract is small and frozen.** Slot names, `data-*` words, and token names are SemVer. Other libraries rename internals and call it a minor release. We treat those names as the product, because every theme and every override hangs on them.

**Overrides are first-class.** You should not need `!important` or a seven-layer specificity tower. Pass a class, or target `[data-intent="danger"]`. We support that path instead of hiding the DOM behind an unreadable `styled()` tree.

**One core, many skins - to be implemented.** A Material-ish or Ant-ish theme is a stylesheet over the same components, not a fork. You are not choosing “the MUI way of dialogs” versus “the Ant way of dialogs.” You choose a look.

**Behavior stays ours; domain UI stays yours.** We allow — and prefer — the inbox row, the job filter, and the brand banner to live in the app and compose Proteus. The library is primitives plus a few hard widgets (dialog, select, tooltip), not a second product.

If you need a data grid next week, use someone else’s. If you want buttons, inputs, and dialogs that still look like _your_ product in two years, this is the shape we think libraries should have been all along.

## What we will not do

Core does not pick your brand colors. The theme does not run a focus trap. Those jobs stay on their own sides of the fence.

We are not racing MUI on component count. Job-specific UI stays in the app.

A future `theme-material-like` would _look_ like Material. It would still _behave_ like Proteus.

Components do not add outer margin. If two things need a gap, that is your layout’s problem — Stack, Grid, or a few lines of CSS.

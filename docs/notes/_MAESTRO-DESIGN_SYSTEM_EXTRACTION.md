# Design System Extraction Guide

This document lists all design tokens, components, styles, animations, and UI elements that need to be extracted from the Form Flow Maestro project when creating a **code-first, token-driven, generator-based design system** with framework adapters.

## Architecture Alignment

This extraction guide aligns with the architecture defined in:

- `design_system_and_component_library_separation_adapter_architecture.md`
- `design_system_theme_generator_parameters_architecture.md`
- `design_system_vs_component_library_architecture_adapters.md`

### Token Hierarchy

Following the established architecture, tokens are organized in three layers:

1. **Primitive Tokens** - Raw values (hex colors, pixel values, etc.)
2. **Semantic Tokens** - Intent-based tokens (`color.action.primary`, `spacing.md`)
3. **Component Tokens** - Component-specific mappings (optional, for complex UI)

> **Critical Rule**: Components must never reference primitive tokens directly. They must consume semantic or component tokens only.

```typescript
    // Needs to be defined based on current grayscale usage

```

```typescript
mode: "light" | "dark"; // Currently only light mode exists
```

## Migration Strategy

This migration strategy follows the architecture defined in the design system documents.

### Phase 1: Extract Primitives

1. Create `tokens/primitives.ts` with all raw values
2. Document all primitive tokens found in this extraction
3. Ensure no components import primitives directly

### Phase 2: Implement Theme Generator

1. Define `ThemeInput` interface per `design_system_theme_generator_parameters_architecture.md`
2. Implement `createTheme()` function
3. Generate semantic tokens from primitives
4. Add contrast calculation for `on-*` tokens

### Phase 3: Create Semantic Tokens

1. Map all primitives to semantic tokens
2. Define token structure per architecture
3. Ensure semantic tokens reference primitives, not components

### Phase 4: Build Adapter Layer

1. Create CSS variable adapter (derived from semantic tokens)
2. Create TypeScript token adapter
3. Ensure adapters are replaceable and isolated
4. Generate CSS variables at build-time or runtime

### Phase 5: Component Library (Framework-Specific)

1. Create React component library (for Next.js and Chrome extension)
2. Components consume semantic tokens via adapters
3. Enforce variant constraints (e.g., `ButtonVariant = 'primary' | 'secondary'`)
4. Implement component tokens for complex UI (optional)

### Phase 6: Migration Execution

1. Replace hardcoded values with semantic token references
2. Update CSS to use CSS variables (derived from tokens)
3. Update TypeScript components to use token objects
4. Maintain backward compatibility during transition

### Phase 7: Enforcement

1. Add linting rules to prevent primitive imports in components
2. Add TypeScript types to enforce token usage
3. Document usage rules per `design_system_color_architecture_summary_next_steps.md`
4. Code review guidelines for token adherence

### Migration Rules (Non-Negotiable)

Per the architecture documents:

1. **No hex values outside `primitives.ts`**
2. **Components never import primitives**
3. **All text uses semantic text tokens**
4. **Colored backgrounds must use matching `on-*` text tokens**
5. **New colors require semantic justification**
6. **Visual similarity ≠ semantic equivalence**

### Breaking Changes

- CSS class names may change to align with component library
- Direct color/spacing values in components will break
- Component APIs will be more constrained (intentional)
- File structure will follow design system architecture

### Backward Compatibility Strategy

1. **Deprecation Period**: Maintain old class names with warnings
2. **Migration Utilities**: Provide codemods for common patterns
3. **Documentation**: Clear migration guides per component
4. **Gradual Migration**: Support both old and new systems during transition

### Testing Strategy

1. **Visual Regression**: Ensure visual parity after migration
2. **Component Unit Tests**: Test component variants and states
3. **Integration Tests**: Test component interactions
4. **Accessibility Audits**: Verify contrast ratios and ARIA attributes
5. **Token Validation**: Ensure all tokens are used correctly
